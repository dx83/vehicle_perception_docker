# 병렬 처리 기반 객체 거리 인식

검토 대상: `vehicle_perception_runtime_fix`의 현재 코드와 `config.yaml`  
검토일: 2026-10-02  
원본 문서: `vehicle_perception_description.md` — 원본은 변경하지 않음

이 문서는 개발 단계의 목표 구조나 이전 서버의 측정값이 아니라, 현재 런타임에 실제 구현된 동작을 설명한다. 추론 엔진과 외부 시각화·전송·저장 프로그램을 구분한다.

## 1. 문서 목적과 프로젝트 목표

이 프로젝트는 카메라 프레임에서 사람, 차량, 이륜차를 인식하고, 객체별 추적 ID와 마스크 내부의 깊이 대표값을 계산하는 경량 추론 라이브러리다.

핵심 목표는 다음과 같다.

- YOLO 인스턴스 세그멘테이션으로 객체의 위치와 픽셀 영역을 얻는다.
- BoT-SORT로 프레임 간 객체를 연결한다.
- UniDepth V2로 같은 입력 프레임의 깊이맵을 추정한다.
- 객체 마스크 내부에서 양수이고 유한한 깊이값의 정확한 중앙값을 계산한다.
- 객체 ID, 클래스, bbox, 원본 거리, 거리 구간, 상태를 메모리상의 결과 객체로 반환한다.
- 세그멘테이션과 Depth의 동시 실행 및 프레임 간 파이프라이닝으로 처리량을 높인다.

한 문장으로 요약하면 다음과 같다.

> 입력 프레임의 세그멘테이션과 깊이 추론을 동시에 시작하고, 세그멘테이션 결과를 추적한 뒤 마스크별 깊이 중앙값과 lifecycle 상태를 결합해 `InferenceResult`를 반환하는 객체 거리 인식 런타임이다.

이 런타임 자체가 브라우저 화면이나 결과 AVI를 만드는 것은 아니다. 그런 기능은 반환 결과를 사용하는 외부 프로그램의 역할이다.

## 2. 구현 범위와 외부 시스템의 역할

### 2.1 런타임에 포함되는 기능

- 프레임 입력 형식 검증
- 로컬 YOLO 세그멘테이션 모델 및 UniDepth V2 모델 로딩
- 객체 클래스 매핑과 BoT-SORT 추적
- 마스크 기반 거리 계산과 거리 구간 분류
- 추적 이력에 따른 거리 변화 및 재등장 상태 관리
- 단일 프레임 처리와 순서 보장 스트리밍 처리
- 메모리상의 진단 정보 제공
- 요청한 경우 공개 결과에 객체 마스크 포함

### 2.2 외부 계층에서 수행할 기능

- 스마트폰·WebRTC·카메라·영상 파일에서 프레임 수신 또는 읽기
- bbox, ID, 거리 텍스트, 마스크, 색상 오버레이
- 브라우저 표시, JPEG 변환, HTTP/WebSocket/WebRTC 전송
- AVI 등 영상 인코딩 및 파일 저장
- JSON/CSV/이미지/업무 로그 저장
- FastAPI, DB, 경보 시스템과 연결

현재 핵심 엔진에는 이러한 업무 산출물 writer가 들어 있지 않다. writer가 없어도 추론은 동작한다. `artifacts.enabled`는 `false`만 허용하며, `true`로 바꾼다고 저장 기능이 활성화되는 구조가 아니다.

### 2.3 현재 구현에 포함되지 않는 판단

차선·Ego corridor 판정, TTC 계산, 충돌 위험 확정, 차량 범퍼 기준 거리 변환, 객체의 최근접 표면 거리 계산은 이 런타임의 기능이 아니다. `NEAR`라는 표시는 거리 구간일 뿐, 실제 충돌 위험이 검증되었다는 뜻이 아니다.

## 3. 세그멘테이션·Depth·Tracking을 결합하는 이유

세 모듈은 서로 다른 정보를 제공한다.

| 모듈 | 제공하는 정보 | 제공하지 않는 정보 |
|---|---|---|
| Segmentation | 객체 클래스, bbox, confidence, 인스턴스 마스크 | 객체의 미터 단위 거리 |
| Depth | 프레임의 픽셀별 추정 깊이 | 객체 ID와 클래스 |
| Tracking | 탐지 결과와 기존 track의 연결 | 새로운 깊이값이나 거리 정확도 보장 |

BBox 전체에서 깊이를 읽으면 객체 외의 도로·배경이 섞일 수 있다. 마스크를 이용하면 모델이 객체라고 분할한 픽셀만 선택할 수 있다. 다만 마스크가 잘못되거나 깊이맵 자체가 틀리면 거리도 틀릴 수 있으므로, 마스크 사용이 언제나 정확도 향상을 보장하지는 않는다.

Tracking은 같은 객체의 시간적 이력을 연결하는 역할이다. 추적 ID가 있다고 해서 깊이 예측의 오차가 자동으로 보정되거나 거리값이 자동으로 평균화되는 것은 아니다.

## 4. 실제 병렬 처리 구조

### 4.1 한 프레임의 의존 관계

```text
외부에서 전달한 원본 BGR 프레임
          │
          ├── Segmentation worker / CUDA stream A
          │        │
          │        └── 클래스 매핑 → Tracking + 공유 GMC (CPU)
          │                               │
          └── Depth worker / CUDA stream B│
                   │                      │
                   └──────────┬───────────┘
                              │
                    Mask + Depth 거리 계산
                              │
                    추적 정보와 객체별 결합
                              │
                      Lifecycle (CPU)
                              │
                    InferenceResult 반환
                              │
              [외부 선택 기능: Overlay / 전송 / 저장]
```

`PerceptionEngine._schedule()`은 원본 프레임을 두 worker에 전달하여 세그멘테이션과 Depth를 함께 시작한다. Depth는 세그멘테이션 결과나 마스크를 입력으로 받지 않는다.

`_commit()`은 세그멘테이션 완료를 기다린 뒤 Tracking을 수행한다. 이때 Depth는 독립적으로 진행 중이거나 이미 끝나 있을 수 있다. 이후 Depth 완료를 확인하고 거리 계산과 lifecycle 처리를 수행한다.

따라서 정확한 설명은 **“Segmentation과 Depth를 동시에 시작하고, Segmentation 뒤에 Tracking을 수행한다”**이다. **“Segmentation이 끝난 다음 Tracking과 Depth를 시작한다”**가 아니다.

### 4.2 같은 GPU의 두 stream

기본 CUDA 실행 경로에서는 세그멘테이션과 Depth가 동일하게 설정된 GPU를 사용하되 서로 다른 CUDA stream에 제출된다. 각 모델용 thread pool에는 worker가 하나씩 있다.

두 stream을 사용한다는 것은 multi-GPU를 사용한다는 뜻이 아니다. 또한 GPU 연산이 항상 완전히 겹친다는 보장도 아니다. 두 모델은 같은 GPU의 연산 자원·메모리 대역폭을 공유하며 CPU 작업과 동기화 비용도 존재한다.

### 4.3 여러 프레임의 bounded pipeline

`process_stream()`은 입력 iterable을 읽는 worker와 bounded FIFO를 사용한다.

- 입력 queue capacity: `3`
- 최대 in-flight 프레임: `3`
- 모델 처리 group size: `1`
- 결과 commit: 입력 순서
- Tracking과 Lifecycle: 순차 commit 경로의 단일 writer

이는 B1 프레임 작업을 파이프라인에 최대 3개 예약해 두는 구조다. 세 프레임을 하나의 batch로 추론하거나 같은 모델을 세 worker에서 동시에 실행하는 구조가 아니다.

정상적으로 입력을 끝까지 소비하는 경우 코어는 queue가 찼을 때 생산자를 기다리게 하며, 임의의 frame skip이나 최신 프레임으로의 교체를 하지 않는다. 외부 실시간 수신 계층에서 이미 프레임을 버렸거나 처리 중 오류·조기 중단이 발생한 경우까지 모든 프레임 처리를 보장하는 것은 아니다.

### 4.4 프레임 0·1·2의 실행 순서 예시

다음은 작업의 순서와 의존 관계를 나타낸 예시다. 각 칸의 길이는 실제 소요 시간을 뜻하지 않으며, GPU에서 정확히 얼마나 겹쳐 실행되는지는 실측해야 한다.

```text
예약:              프레임 0 → 프레임 1 → 프레임 2

Segmentation lane: Seg0 → Seg1 → Seg2 → …
Depth lane:        Dep0 → Dep1 → Dep2 → …
                   ↑ 두 lane은 독립 worker와 CUDA stream 사용

순차 commit:
  Seg0 완료 확인 → Track0 → Dep0 완료 확인 → Fusion0 → Lifecycle0 → 결과 0
  Seg1 완료 확인 → Track1 → Dep1 완료 확인 → Fusion1 → Lifecycle1 → 결과 1
  Seg2 완료 확인 → Track2 → Dep2 완료 확인 → Fusion2 → Lifecycle2 → 결과 2
```

프레임 0의 commit 중에도 다음 프레임의 모델 작업은 진행될 수 있다. 다만 같은 lane의 모델 작업은 worker 하나에서 차례로 수행한다. 먼저 모델 추론이 끝난 프레임이 있더라도 Tracking·Lifecycle 갱신과 결과 반환 순서를 임의로 바꾸지 않는다.

현재 스트림은 in-flight 작업이 3개에 도달하면 가장 오래된 프레임을 commit한다. 입력이 3개보다 적고 종료되면 남은 작업을 순서대로 처리한다. 따라서 무한 실시간 입력에서는 초기 프레임을 모으는 시간도 첫 결과의 지연에 영향을 줄 수 있다.

### 4.5 Bounded queue와 장시간 메모리 사용은 별개

입력 queue와 in-flight 수를 제한한다고 해서 엔진 전체의 메모리 사용량까지 항상 일정한 것은 아니다. 현재 구현에는 다음 누적 구조가 있다.

- `OrderedStreamPipeline.run()`의 `committed_indices`와 `frame_latencies`는 스트림 전체의 처리 이력을 목록으로 보관한다. 같은 스트림이 길어질수록 항목이 늘어난다.
- `Tracker`의 `_identities`, `_history`는 관측된 track ID별 정보를 보관하며, 오래된 ID를 주기적으로 정리하는 코드가 없다.
- `Lifecycle`의 `_last`와 일부 거리 `_history`도 ID별 상태를 보관한다. 거리 무효화·재등장 reset 등으로 일부 이력은 지워지지만 모든 오래된 ID를 만료시키는 정책은 없다.

> 현재 제한된 것은 프레임 대기열과 in-flight 수다. 장시간 단일 스트림에서 전체 RAM/VRAM 사용량이 일정하게 유지된다고 검증된 것은 아니다.

진단 목록은 스트림 실행 범위의 이력이며 프레임 영상 전체를 저장하는 것은 아니다. 새 스트림에서 tracker와 lifecycle은 reset되지만, 이를 위해 임의로 스트림을 끊으면 track ID 연속성도 끊어진다. 장시간 운용에는 처리 시간·누적 프레임 수·새 ID 수에 따른 메모리 추이를 별도로 확인해야 한다. 이는 현재 코드의 주의사항이며, 이 문서 보강에서 이력 정책을 변경한 것은 아니다.

## 5. 입력과 공개 API

### 5.1 입력 프레임

입력은 비어 있지 않은 `numpy.ndarray`이며, `uint8` 타입의 `H × W × 3` OpenCV BGR 이미지여야 한다.

입력은 반드시 1600×900 또는 12 FPS일 필요가 없다. 다만 실제 입력 크기·crop·회전 등에 맞는 카메라 내부 파라미터가 필요하고, 해상도가 바뀌면 처리 시간과 모델 compile 동작도 달라질 수 있다.

### 5.2 `process(frame, timestamp=None)`

단일 프레임을 처리해 `InferenceResult` 하나를 반환한다. 한 프레임 안에서도 세그멘테이션과 Depth의 동시 실행을 사용한다. 반복 호출 시 같은 엔진의 추적·거리 이력이 이어진다.

`timestamp`를 전달하면 해당 값을 사용한다. 생략하면 호출 시점의 `time.time()`을 사용한다. 영상의 원래 촬영 시각이나 파일의 PTS를 자동으로 읽는 기능은 없다.

### 5.3 `process_stream(frame_source)`

프레임 iterable을 받아 결과를 입력 순서대로 yield한다. 새 스트림을 시작할 때 tracker와 lifecycle을 reset하고 `frame_id`를 0부터 다시 부여한다. 따라서 같은 엔진으로 여러 영상이나 replay를 처리해도 스트림 사이의 track ID는 이어지지 않는다.

이 API의 timestamp는 producer가 프레임을 입력받은 시점이다. 원본 카메라 capture timestamp와 같다고 간주하면 안 된다.

### 5.4 초기화·warmup·종료

모델은 엔진 생성 시 로딩하며 매 프레임 재로딩하지 않는다. `warmup()`은 모델 경로를 미리 실행하여 compile 및 초기 실행 비용을 준비하되 추적·lifecycle 상태를 진행시키지 않는다. 사용 후 `close()`로 worker와 상태를 정리한다.

하나의 엔진에 `process()`나 `process_stream()`을 동시에 호출하는 사용 방식은 지원하지 않는다. 내부 worker 병렬 처리와 외부에서 엔진을 동시 호출하는 것은 서로 다른 문제다.

## 6. 단계별 구현과 사용 기술

### 6.1 Segmentation — `segmentation.py`

현재 기본 모델은 `yolo26m-seg.pt`다. `Segmenter.predict()`는 bbox, 원래 모델 클래스명, confidence, 인스턴스 마스크를 반환한다.

YOLO는 한 번의 모델 추론으로 객체 위치·클래스와 분할 결과를 얻는 방식으로 사용된다. 객체마다 별도의 binary mask가 있으며, 모델이 예측한 영역을 거리 계산의 픽셀 선택 기준으로 삼는다.

현재 클래스 매핑은 다음과 같다.

| 모델 클래스 | 공개 결과의 `class_name` |
|---|---|
| `car`, `truck`, `bus` | `vehicle` |
| `person` | `person` |
| `bicycle`, `motorcycle` | `two_wheeler` |

`vehicle`과 `two_wheeler`는 이 프로그램의 응용 그룹이다. YOLO 모델의 원래 label이 모두 이 이름으로 학습되었다는 뜻은 아니다. 설정에 없는 클래스는 엔진의 객체 결과에서 제외된다.

`retina_masks=True`로 마스크를 요청하고, 크기가 입력 프레임과 다르면 nearest 방식으로 정렬한다. binary mask 기준은 `> 0.5`다.

기본 CUDA 경로에서 마스크는 GPU tensor로 유지한다. bbox·클래스·confidence는 추적과 결과 구성을 위해 CPU로 가져온다. 따라서 “세그멘테이션 결과 전체가 CPU로 내려갔다가 거리 계산에서 다시 GPU로 올라간다”는 설명은 현재 코드와 맞지 않는다.

### 6.2 Tracking — `tracking.py`

현재 정책은 **BoT-SORT, ReID OFF, sparseOptFlow GMC 유지**다. GMC OFF나 ByteTrack으로의 교체를 현재 구현으로 설명하면 안 된다.

`Tracker`는 `person`, `two_wheeler`, `vehicle`별로 group tracker를 관리한다. GMC의 warp는 프레임마다 한 번 계산하고 세 group tracker에 공유한다.

추적의 주요 요소는 다음과 같다.

- Kalman 기반 위치·운동 상태 예측
- 현재 detection과 기존 track 사이의 data association
- LAP 기반 할당을 위한 `lap` 의존성
- 카메라 움직임의 영향을 줄이기 위한 GMC
- 그룹 내부 ID를 공개용 고유 ID로 매핑

프로젝트가 직접 Hungarian 알고리즘을 구현한 것은 아니다. 실제 연관 계산은 설치된 Ultralytics BoT-SORT 구현과 그 의존성을 이용한다.

ReID가 꺼져 있으므로 별도의 외형 특징 추론을 통한 장기 재식별을 사용하지 않는다. ID switch나 track fragmentation은 발생할 수 있다. 현재 관측이 track에 연결되지 않으면 `track_id=None`으로 반환할 수 있다.

현재 프레임에 탐지되지 않은 객체에 대해 예측 bbox나 거리 객체를 별도로 만들어 반환하지 않는다. 내부 track 유지와 공개 결과의 관측 객체 출력은 구분해야 한다.

#### 현재 tracker에 실제로 들어오는 confidence 범위

기본 설정은 YOLO의 `inference.confidence=0.25`, tracker의 `track_high_thresh=0.25`, `track_low_thresh=0.1`이다.

하지만 tracker는 YOLO가 반환한 detection만 받는다. 따라서 기본 모델 경로에서는 **confidence가 0.1 이상 0.25 미만인 탐지를 YOLO 단계에서 이미 제외**하며, tracker는 이 탐지들을 저신뢰도 연관에 활용할 수 없다.

`track_low_thresh=0.1`이라는 설정만 보고 0.1부터의 detection이 실제로 전달된다고 설명하면 안 된다. 이는 현재 상위 탐지 필터와 tracker 입력의 관계이며, BoT-SORT가 지원하는 모든 경로를 현재 설정에서 온전히 활용한다는 뜻은 아니다. 이 문서에서는 임계값이나 알고리즘을 변경하지 않는다.

### 6.3 Depth — `depth.py`

기본 모델 폴더는 `unidepth-v2-vitb14`이며 현재 설정은 **UniDepth V2 ViT-B, `resolution_level=3`**이다. “ViT-S / ViT-B를 사용하는 모델”처럼 현재 모델을 모호하게 적지 않는다.

`DepthEstimator`는 `RuntimeConfig`에서 모델 경로, device, 카메라 K, resolution level을 받는다. 로컬 모델 폴더의 `config.json`과 `model.safetensors`를 확인하고 `UniDepthV2.from_pretrained(..., local_files_only=True)`로 읽는다.

`config.json`은 모델 구조·설정 파일이고 `model.safetensors`는 학습된 가중치다. 두 파일은 현재 로더에 필요하다. `stage24_model_provenance.json`이나 과거 모델 ID/revision 상수는 이 런타임의 필수 입력이 아니다.

모델 경로를 변경할 수 있지만 로더는 `UniDepthV2`로 고정되어 있다. 임의의 다른 Depth 모델을 경로만 바꿔 사용할 수 있는 범용 backend 구조는 아니다.

추론 시 BGR 입력을 RGB tensor로 변환하고 설정된 K를 함께 전달한다. `encode_decode`에는 `torch.compile(mode="default", fullgraph=False)`를 적용한다. 결과의 `depth`는 입력 해상도와 같은 `(1, 1, H, W)`인지 검사하고 GPU tensor로 유지한다.

런타임 코드에는 별도의 CUDA optimized op 설치·활성화 절차가 없다. 따라서 과거 최적화 단계 이름이나 설치 여부만으로 해당 연산을 현재 엔진이 사용한다고 단정하지 않는다.

### 6.4 Mask–Depth 거리 계산 — `distance.py`

`fuse_distances()`가 하는 일은 **마스크와 Depth를 결합하여 객체별 raw distance를 계산하는 것**이다. 이 함수 자체가 Tracking이나 Lifecycle을 실행하지는 않는다. 추적 정보와의 결합은 `engine.py`에서 수행한다.

객체 `i`의 binary mask를 `M_i`, 깊이맵을 `D`라고 하면 선택하는 값은 다음과 같다.

```text
V_i = { D[y, x] | M_i[y, x] = True,
                    D[y, x] > 0,
                    D[y, x]가 유한함 }

raw_distance_i = median(V_i)
```

빈 마스크이거나 유효 깊이값이 하나도 없으면 거리값은 `None`이다. 0m나 이전 거리값으로 임의 대체하지 않는다.

중앙값은 `kthvalue` 기반으로 정확하게 계산한다. 값 개수가 홀수면 가운데 값, 짝수면 가운데 두 값의 평균을 사용한다. 현재 방식은 평균·하위 분위수·중심점 값 중 하나를 자동으로 고르는 방식이 아니라 `mask_exact_median`으로 고정되어 있다.

중앙값은 극단적인 일부 값에 평균보다 덜 민감하지만, 깊이맵 전체의 scale 오차나 마스크 대부분의 잘못된 픽셀을 해결하지는 못한다.

CUDA 경로에서는 마스크 선택·양수/유한값 필터·중앙값 계산을 GPU에서 수행한다. 마지막에 객체별 마스크 픽셀 수, 유효 픽셀 수, 거리 같은 소수의 scalar를 CPU로 가져와 Python 결과를 만든다. `.cpu().numpy()`가 있다는 이유만으로 마스크 내부 통계 전체가 CPU 연산이라는 뜻은 아니다. 다만 데이터 이동과 동기화 비용은 있으므로 비용이 0이라고 설명하지도 않는다.

#### 거리 계산 성공과 거리 신뢰도는 다르다

현재는 마스크 내부에 유효한 깊이값이 하나라도 있으면 중앙값을 계산한다. 최소 마스크 면적, 최소 유효 픽셀 수·비율, 깊이 분산 등에 따른 거리 품질 gate는 구현되어 있지 않다.

따라서 다음처럼 품질이 부족할 수 있는 경우도 수치가 반환될 수 있다.

- 작은 객체 마스크에서 극소수의 유효 픽셀만 남은 경우
- 마스크 대부분의 깊이는 무효이고 일부만 유효한 경우
- 깊이값이 여러 수준으로 넓게 분산되거나 배경이 많이 섞인 경우

**거리값이 계산되었다는 것은 정확도나 충분한 표본 수가 확보되었다는 뜻이 아니다.** positive finite 필터는 수치의 사용 가능 여부를 거르는 것이지, 거리의 물리적 정확도를 판정하는 검증기가 아니다.

공개 `confidence`는 세그멘테이션 모델의 객체 탐지 confidence다. 거리 추정의 confidence, 오차 범위, 정확할 확률을 뜻하지 않는다. 현재 공개 결과에는 별도의 거리 품질 점수나 유효 픽셀 비율·깊이 편차가 없다. Lifecycle 상태도 GT에 근거한 거리 신뢰도 점수는 아니다.

### 6.5 Lifecycle — `lifecycle.py`

`Lifecycle.process()`는 거리 계산과 추적 정보 결합 이후 별도로 실행한다. 객체 이력을 이용해 거리 점프 의심, 재등장, 이력 reset 등의 상태를 판단한다.

현재 거리 변화 정책의 주요 기준은 다음과 같다.

- 충분한 이력이 있는 confirmed track에 대해 판단한다.
- 절대 변화가 8m 이상이고 상대 변화가 45% 이상인 경우 급격한 변화로 본다.
- 조건에 맞으면 내부 `display_distance_m`을 이전 값으로 한 프레임만 유지할 수 있다.
- 다음 연속 관측에서 이전 수준 복귀·새 수준 유지·불확실한 변화를 구분한다.
- 두 번째 연속 hold는 하지 않는다.
- 탐지 gap이나 재등장 위치 불연속에 따라 이력을 reset하거나 pending 상태를 끝낸다.
- 유효한 현재 거리가 없으면 거리를 만들어내지 않는다.

BBox 겹침으로 계산한 `occlusion_proxy`는 가림 의심의 대리 지표다. 실제 가림 정답이나 물리적인 가림 정도를 측정한 값은 아니다.

가장 중요한 공개 API상의 구분은 다음과 같다.

> Lifecycle 내부에는 `display_distance_m`이 있지만, 현재 `DetectedObject.distance_m`은 항상 `raw_distance_m`을 사용한다. `distance_zone`도 raw 값으로 계산한다.

따라서 `state="HELD_ONE_FRAME"`이어도 공개 `distance_m`이 이전 값으로 바뀌는 것은 아니다. 현재 공개 결과에는 `display_distance_m` 필드가 없다. “최종 반환 거리가 한 프레임 hold로 안정화된다”거나 “오버레이가 자동으로 hold 값을 표시한다”는 설명은 틀리다.

이 모듈은 moving average나 EMA를 적용하는 일반적인 smoothing filter도 아니다.

#### Raw 거리와 내부 hold의 숫자 예시

아래는 같은 confirmed track에 충분한 이력이 있고 gap·reset이 없는 경우의 예시다. 모든 track에서 무조건 이렇게 처리되는 것은 아니다.

| 관측 | 현재 raw 거리 | 내부 `display_distance_m` | 공개 `distance_m` | 거리 상태 |
|---|---|---|---|---|
| 이전 안정 관측 | 20m | 20m | 20m | `NORMAL` |
| 급격한 변화 | 35m | 20m로 한 프레임 hold | 35m | `HELD_ONE_FRAME` |
| 다음 관측에서 이전 수준으로 복귀 | 21m | 21m | 21m | `OUTLIER_REJECTED` |

20m에서 35m로 변하면 절대 변화는 15m, 이전 20m 대비 상대 변화는 75%다. 두 jump 조건을 만족하면 내부 hold가 가능하지만, 공개 거리와 거리 구간은 여전히 현재 raw 35m를 기준으로 한다.

다음 값이 21m라면 이전 수준 20m와의 차이가 5%이므로 내부 정책은 이전 35m 관측을 이상치로 분류한다. 그러나 과거 반환 결과를 수정하거나 현재 공개 거리를 20m로 덮어쓰지는 않는다. 이 예시의 `OUTLIER_REJECTED` 역시 현재값을 제거한다는 뜻이 아니라 이전 pending 관측에 대한 판정이다.

#### Gap과 이력 기준은 초가 아니라 프레임 수

현재 gap과 이력 길이는 엔진이 처리한 프레임 번호로 계산한다. `timestamp`를 이용한 경과 시간 기반 정책이 아니다. 8m/45% jump도 시간으로 나눈 속도나 TTC가 아니라 관측 간 거리 변화 조건이다.

등간격 입력이라고 가정하면 2프레임 간격은 30 FPS에서 약 67ms, 10 FPS에서 약 200ms다. 같은 프레임 수 기준이라도 입력 빈도에 따라 실제 시간상 의미가 달라진다.

외부 수신 계층이 촬영 프레임을 버린 뒤 나머지 프레임만 전달하면 엔진은 전달받은 프레임을 다시 연속 번호로 처리한다. 이 경우 촬영 시점의 긴 공백을 엔진의 frame gap만으로 알 수 없다. 스마트폰·네트워크 입력에서는 촬영 시각과 실제 수신 간격을 외부에서 별도로 확인해야 한다.

## 7. 반환 결과와 마스크 전달

`result.py`의 공개 결과는 frozen dataclass다. JSON 파일이나 이미지가 아니라 Python 객체로 반환된다.

### 7.1 `InferenceResult`

| 필드 | 의미 |
|---|---|
| `frame_id` | 엔진이 부여한 프레임 번호 |
| `timestamp` | API에 전달했거나 엔진에서 생성한 시각 |
| `objects` | 현재 관측 객체의 `DetectedObject` tuple |

### 7.2 `DetectedObject`

| 필드 | 의미 |
|---|---|
| `track_id` | 연결된 추적 ID 또는 `None` |
| `class_name` | `person` / `vehicle` / `two_wheeler` 응용 그룹 |
| `confidence` | 세그멘테이션 모델의 객체 confidence. 거리 정확도의 신뢰도가 아님 |
| `bbox` | 입력 프레임 좌표의 `(x1, y1, x2, y2)` |
| `distance_m` | 현재 마스크의 raw depth median 또는 `None` |
| `distance_zone` | raw 거리에 따른 `NEAR` / `MID` / `FAR` / `UNKNOWN` |
| `state` | 거리 상태. 예: `NORMAL`, `NEW_TRACK`, `HELD_ONE_FRAME` |
| `lifecycle_state` | `OBSERVED`, `REAPPEARED`, `HISTORY_RESET` |
| `mask` | 요청한 경우 `MaskGeometry`, 기본은 `None` |

내부 `object_index`는 현재 세그멘테이션 결과의 순서에 따른 번호다. 객체의 영구 ID가 아니며 공개 `DetectedObject` 필드에도 없다. 물리적 객체 동일성을 비교할 때 이 번호만으로 연결해서는 안 된다.

### 7.3 `MaskGeometry`

`return_masks=True`로 엔진을 생성한 경우 객체 마스크의 최소 ROI를 반환한다. `x`, `y`, `width`, `height`는 원본 프레임에서의 ROI 위치·크기이고, `packed_bits`는 binary mask를 `np.packbits(bitorder="big")`로 압축한 bytes다. JPEG 이미지나 확률맵이 아니다.

공개 결과용 마스크를 만들 때는 요청한 ROI를 GPU에서 CPU로 복사해 pack한다. 기본 `return_masks=False`에서는 이 공개 마스크 변환을 하지 않는다. 마스크를 반환하지 않더라도 내부 거리 계산에는 마스크를 계속 사용한다.

## 8. 거리값의 의미와 카메라 설정

### 8.1 무엇을 측정하는가?

코드에서 직접 확인할 수 있는 정의는 **“UniDepth V2가 반환한 `depth` 중 객체 마스크 내부 positive finite 값의 median”**이다. 이를 미터 단위 추정 거리로 사용한다.

객체는 여러 표면으로 구성되므로 이 값은 관측된 마스크 픽셀들의 대표 깊이다. 객체 중심점의 거리, 가장 가까운 표면 거리, 실제 bumper-to-object 거리와 같다고 보장하지 않는다.

이 코드에는 `points`의 XYZ norm을 이용한 Euclidean range 계산, 차량 좌표계 변환, 카메라 외부 파라미터 적용, 범퍼 offset 보정이 없다. 따라서 단순히 “카메라에서 객체까지의 정확한 직선거리”라고 설명하는 것은 부정확하다.

### 8.2 K는 실제 입력에 맞아야 한다

카메라 내부 행렬은 보통 다음 형태다.

```text
K = [[fx,  0, cx],
     [ 0, fy, cy],
     [ 0,  0,  1]]
```

`fx`, `fy`는 픽셀 단위 초점거리이고 `cx`, `cy`는 주점 좌표다. 현재 YAML에 있는 값은 특정 카메라 설정값이며 모든 카메라나 스마트폰에 공통으로 맞는 값이 아니다.

카메라, 해상도, crop, digital zoom, 회전이 달라지면 그 조건에 맞는 K를 준비해야 한다. 엔진은 실제 카메라를 자동 보정하거나 입력 해상도 변경에 따라 YAML의 K를 자동 수정하지 않는다.

현재 설정 검증은 K가 3×3이고 숫자로 변환되는지 확인하는 수준이다. 설정 파일을 읽었다는 사실만으로 카메라 보정이 유효하다고 판단해서는 안 된다.

### 8.3 현재 거리 구간

| 구간 | 현재 기본 조건 |
|---|---|
| `UNKNOWN` | 거리 없음, 비유한 값 또는 0 이하 |
| `NEAR` | `0 < distance_m <= 15` |
| `MID` | `15 < distance_m <= 40` |
| `FAR` | `distance_m > 40` |

15m와 40m는 `config.yaml`의 현재 기본값이다. 10m/20m가 아니다. 구간 경계는 설정으로 바꿀 수 있지만, 빨강·노랑·초록 등 색상 선택은 런타임이 아니라 외부 renderer의 정책이다.

| `models.depth` | `unidepth-v2-vitb14` | 로컬 UniDepth V2 모델 폴더 |
| `paths.model_root` | `../models` | YAML 파일 위치 기준 모델 루트 |
| `paths.runtime_root` | `../runtime_root` | 설정에 보관하는 경로. 현재 엔진의 산출물 저장 기능이 아님 |
| `device.type` / `gpu_id` | `cuda` / `0` | 논리 device `cuda:0` |
| `inference.confidence` | `0.25` | YOLO confidence 기준 |
| `inference.resolution_level` | `3` | UniDepth V2 resolution level |
| `pipeline` | `3 / 3 / 1` | queue / in-flight / group size 고정 |
| `tracking` | BoT-SORT / sparseOptFlow / ReID OFF | 현재 정책과 동일해야 설정 로딩 가능 |
| `distance.method` | `mask_exact_median` | 현재 지원하는 거리 계산 방식 |
| `distance.near_max_m` / `mid_max_m` | `15 / 40` | 거리 구간 경계 |
| `camera.intrinsic` | YAML의 3×3 행렬 | 입력 카메라 K |
| `artifacts.enabled` | `false` | 코어 산출물 저장 금지 |

YAML에 항목이 있다는 이유로 모든 값을 자유롭게 바꿀 수 있는 것은 아니다. `config.py`는 tracking 전체 정책, pipeline 값, 거리 계산 방식 및 artifact OFF를 검사하여 다른 값이면 실패한다.

`gpu_id`는 `CUDA_VISIBLE_DEVICES`를 적용한 뒤 프로그램에서 보이는 논리 번호다. 예를 들어 physical GPU 1만 노출했다면 프로그램 내부 `cuda:0`은 그 physical GPU를 가리킨다. 현재 코드는 자동 GPU 선택이나 fallback 정책을 구현하지 않는다.

### 9.2 모델과 소프트웨어 의존성

모델 파일은 `models/`에서 준비한다. 로컬 YOLO 파일 또는 UniDepth 모델 필수 파일이 없으면 실패하며, 모델 자동 다운로드를 기본 동작으로 사용하지 않는다.

`pyproject.toml`은 Python 3.12, `torch==2.10.0`, `ultralytics==8.4.150`, `lap>=0.5.12`, NumPy, OpenCV, PyYAML 및 UniDepth 소스 의존성을 선언한다.

UniDepth Git commit 지정은 **모델 추론에 필요한 소프트웨어 구현의 버전 지정**이다. 로컬 모델 가중치 경로나 과거 `stage24_model_provenance.json` 요구와는 다른 개념이다. YAML에서 모델 폴더를 바꾼다고 Python 의존성이 자동으로 교체되는 것은 아니다.

CUDA 실행 및 `torch.compile`에는 해당 환경에 맞는 GPU 드라이버와 컴파일 도구 등 실행 환경도 필요하다. “어떤 컴퓨터에서나 같은 FPS로 동작한다”는 뜻이 아니다. 설정은 CPU도 표현할 수 있지만, 이를 CUDA 병렬 성능 검증과 동일한 검증 완료 경로로 간주하지 않는다.

## 10. 사용 형태: 결과를 받은 뒤 외부에서 처리

다음 예시는 호출 구조를 보여준다. `frame`은 외부 카메라·수신 코드가 준비한 BGR 배열이라고 가정한다.

```python
from pathlib import Path
import vehicle_perception_runtime_fix as runtime

config_path = Path(runtime.__file__).resolve().parent / "config.yaml"
engine = runtime.PerceptionEngine(config_path, return_masks=False)

try:
    engine.warmup(frame)
    result = engine.process(frame)
    # result.objects를 외부 FastAPI/DB/renderer 등에 전달한다.
    # 이 호출 자체는 영상, CSV, JSON 같은 업무 파일을 저장하지 않는다.
finally:
    engine.close()
```

프레임 연속 처리에는 같은 엔진의 `process_stream(frame_source)`를 사용한다. 한 프레임마다 엔진을 새로 생성하면 모델 초기화가 반복되고 track 이력도 이어지지 않는다.

현재 `engine.py`의 생성자 기본 설정 경로에는 `vehicle_perceptzion_runtime`라는 오타가 있으므로, 예시처럼 실제 패키지 위치에서 계산한 `config_path`를 명시적으로 전달한다. 이 문서 작업에서는 해당 코드를 수정하지 않았다.

### 10.1 스트리밍 결과와 원본 프레임 연결

`process_stream()`은 `InferenceResult`만 yield하며 원본 프레임을 함께 반환하지 않는다. Overlay를 만드는 외부 계층은 해당 스트림의 입력 순서와 `frame_id`에 맞춰 원본 프레임을 보관·연결해야 한다.

- 결과 0에는 입력 프레임 0을 사용한다. 추론이 끝난 시점에 수신한 최신 프레임을 무조건 사용하는 것은 아니다.
- 처리 중인 원본 프레임에 먼저 Overlay를 그려서는 안 된다. 모델·GMC가 참조하는 입력과 표시용 배열을 구분한다.
- 엔진은 입력 프레임 전체의 독립 복사본을 자동으로 만들지 않는다. 완료 전에 동일 NumPy 배열을 다음 촬영 프레임으로 덮어쓰거나 수정하지 않는다.
- 프레임 저장소도 완료·소비된 항목을 해제하고 크기를 관리한다. 엔진 queue가 bounded라는 이유로 외부 저장소까지 자동 제한되지는 않는다.

프레임 0의 결과를 프레임 3의 이미지에 그리면 bbox와 마스크가 어긋날 수 있다. 이는 추론 정확도 문제가 아니라 이미지와 결과의 대응 문제다.

### 10.2 세션·Track ID와 DB 연동

`track_id`는 모든 실행에 걸쳐 영구적으로 유일한 객체 식별자가 아니다. 새 스트림이나 새 엔진에서는 ID가 다시 부여되고 같은 숫자를 재사용할 수 있다. 또한 ID switch와 재추적에 따른 ID 변경도 가능하다.

외부 시스템에서는 최소한 다음 구분을 유지한다.

- 결과 프레임 식별: `(session_id, frame_id)`
- 스트림 내부 track 식별: `(session_id, track_id)` — ID가 있는 경우
- `track_id=None`인 여러 객체를 하나의 공통 track으로 합치지 않는다.
- 시간상 영구적인 물리적 객체 동일성이 필요한 경우, 이 엔진의 ID만으로 확정하지 않는다.

`session_id`는 현재 `InferenceResult`에 포함되지 않으므로 스마트폰 연결·영상 재생·카메라 세션을 관리하는 외부 계층에서 부여한다. 위 식별자를 추가로 설명하는 것은 API 필드를 새로 구현했다는 뜻이 아니다.

## 11. 성능을 해석하는 방법

### 11.1 한 프레임의 의존 경로

현재 코어를 이상적으로 겹쳐 실행했을 때 한 프레임의 처리 시간은 다음처럼 이해할 수 있다.

```text
T_core ≈ max(T_segmentation + T_tracking, T_depth)
         + T_fusion + T_lifecycle + T_result
```

이는 현재 의존 관계를 설명하는 개념식이지 실측 성능 예측식이 아니다. GPU 자원 경쟁, queue 대기, stream 동기화, CPU 작업, 마스크 반환 비용 등에 따라 달라진다. 거리 계산도 GPU를 사용하므로 다른 프레임의 모델 실행과 경쟁할 수 있다.

기존 문서의 `T_seg + max(T_track, T_depth)`는 Depth가 세그멘테이션 이후 시작한다는 잘못된 전제였다. Overlay와 Encode를 코어의 필수 단계로 더하는 것도 현재 런타임 설명에는 맞지 않는다.

### 11.2 처리량과 지연은 다르다

- 처리량 FPS: 일정 구간에서 완료한 프레임 수 / 실제 경과 시간
- 프레임 latency: 특정 프레임의 입력부터 결과 반환까지 걸린 시간
- 화면 publish FPS: 외부 프로그램이 웹으로 프레임을 내보내는 빈도
- Overlay loop FPS: 외부 renderer·JPEG·전송 등을 포함한 반복 처리 속도

파이프라인에서는 여러 프레임이 겹치므로 평균 latency의 역수가 처리량 FPS와 같지 않을 수 있다. queue에 먼저 예약된 프레임이 많으면 처리량은 좋아져도 한 프레임의 대기시간은 늘 수 있다. 웹 publish를 제한해도 추론을 같은 빈도로 제한했다는 뜻은 아니다.

### 11.3 진단 정보와 실측 조건

`engine.diagnostics`는 최근 프레임의 segmentation, tracking, depth, fusion, lifecycle 시간 및 모델 결과 대기시간을 제공한다. 스트림 종료 후에는 queue·in-flight 최대치, commit 순서, frame loss/duplicate/reorder, worker 종료 여부 등의 진단도 얻을 수 있다.

모델 시간과 대기시간은 겹칠 수 있으므로 단순 합산하면 wall time이 되지 않는다. 모델 초기화와 compile warmup을 포함했는지, 외부 decode·overlay·encode·네트워크를 포함했는지 분리해 기록해야 한다.

기존 문서의 20.48ms, 38.12ms, 35.22ms, 9.40 FPS 및 병목 69% 등은 현재 `vehicle_perception_runtime_fix`의 측정 결과로 입증된 수치가 아니다. 이 문서에서는 현재 성능값으로 사용하지 않는다. 27/30 FPS 역시 현재 코드가 보장하는 성능이나 통과 결과로 제시하지 않는다.

RTX 4070과 RTX 6000 등의 비교도 같은 입력·환경·warmup·실행 경로에서 측정해야 한다. GPU 이름이나 과거 다른 프로젝트의 성능만으로 현재 속도를 확정할 수 없다.

## 12. 검증과 데이터의 관계

기존 개발 프로젝트의 nuScenes GT 대조와 최적화 검증은 개발 이력·외부 검증 자료에 해당한다. 현재 경량 런타임은 nuScenes 데이터, GT CSV, 과거 Matching 산출물 또는 Stage 보고서를 매 프레임 읽어 추론하지 않는다.

현재 코드에는 GT 거리로 raw 값을 보정하는 affine calibration이나 거리 의존형 보정이 없다. 이전 단계의 검증 결과를 현재의 새로운 카메라·해상도·환경에 대한 정확도 보장으로 가져오면 안 된다.

현 환경에서 검증하려면 최소한 다음을 분리해 확인한다.

- 입력에 맞는 카메라 K와 마스크·Depth 좌표 정렬
- 동일 물리적 객체 기준의 detection·track 연결
- positive finite mask median과 공개 raw 거리의 일치
- track ID 변화, gap·재등장·history reset, 한 프레임 hold 정책
- 정상 종료 시 frame loss/duplicate/reorder와 worker 종료 상태
- 업무 산출물 writer 없이 추론 가능한지
- warmup 이후 실제 처리량·프레임 latency·VRAM
- 외부 시각화·전송을 붙였을 때의 별도 end-to-end 성능

이 문서는 코드와 설명을 대조한 결과다. 새로운 GPU 성능 측정이나 거리 GT 정확도 재검증을 수행한 보고서는 아니다.

### 12.1 현재 프로젝트의 실측 근거를 기록하는 형식

현재 문서에는 `vehicle_perception_runtime_fix`를 이 설정 그대로 실행해 새로 확인한 정확도·성능 수치가 없다. 과거 다른 단계의 결과는 historical reference로 구분하며, 검증 자료가 없으면 아래 항목을 임의로 채우지 않는다.

향후 실제 검증 자료를 추가할 때는 다음 조건과 지표를 함께 기록한다.

| 항목 | 기록할 내용 |
|---|---|
| 실행 식별 | 코드 commit 또는 파일 hash, 모델 식별/hash, config, 검증 일시, 원본 결과 경로 |
| 환경 | CPU, 실제 GPU, GPU 점유 상태, OS, Python, Torch/CUDA 및 주요 패키지 버전 |
| 입력 | 영상/카메라, 해상도, 입력 FPS, 프레임 수, K, crop·회전·zoom 조건 |
| Warmup | 초기화·compile·warmup 포함 여부 및 측정 시작 기준 |
| 처리량 | 코어 처리량과 외부 decode·Overlay·전송·저장을 포함한 처리량을 분리 |
| Latency | 시작·종료 시점의 정의, 평균·p95, 촬영 시각 기반인지 엔진 수신 시각 기반인지 |
| 메모리 | peak VRAM 및 장시간 실행의 RAM/VRAM 추이, 누적 프레임·track 수 |
| 거리 정확도 | GT 정의·기준 좌표계, 동일 객체 대응 방법, 평가/제외 객체 수, 거리 구간별 MAE 등 |
| 추적·Lifecycle | ID 변화·gap·reset·hold 사례, frame loss/duplicate/reorder 및 정상 종료 여부 |

GT와 예측값은 같은 거리 정의와 기준점으로 비교해야 한다. 예를 들어 객체 중심의 Euclidean GT와 마스크의 대표 depth를 정의 차이 검토 없이 그대로 비교하면 모델 오차와 측정 대상 차이가 섞일 수 있다.

전체 평균만으로 근거리 정확도를 설명하지 않는다. 구간별 평가 수와 오차를 함께 제시하며, unmatched 객체·유효 거리 없음 등 제외 사유도 기록한다. 단, 실제 검증 없이 근거리 우수, 27/30 FPS 달성, 장시간 안정 동작 등의 결론을 붙이지 않는다.

## 13. 기술 키워드와 정확한 의미

- Instance segmentation: 객체별 픽셀 영역을 분리한다.
- Monocular depth estimation: 단일 영상의 시각적 단서로 깊이를 추정한다.
- ViT-B: 현재 기본 UniDepth V2 모델의 backbone 구분이다.
- MOT / BoT-SORT: 여러 객체의 detection을 시간축에서 track에 연결한다.
- Kalman filter: tracking의 상태 예측·관측 보정에 사용된다. 깊이 보정기가 아니다.
- LAP / data association: detection과 track의 대응을 결정하는 할당 문제다.
- sparseOptFlow GMC: 카메라 움직임 보정을 위한 warp를 계산하며 현재 유지되어 있다.
- Exact mask median: 객체 마스크 내부 positive finite 깊이값의 정확한 중앙값이다.
- Lifecycle: 거리 이력과 재등장·거리 변화 상태를 관리한다. 공개 raw 값을 smoothing하지 않는다.
- Bounded ordered pipeline: queue와 in-flight 수를 제한하며 입력 순서로 상태를 갱신한다.
- Artifact-free core: 업무 파일 저장 없이 결과 객체를 반환한다. 라이브러리의 compile cache 같은 환경 동작까지 전혀 없다는 뜻은 아니다.

## 14. 주요 정정 사항과 구현 근거

| 기존 설명에서 수정한 부분 | 현재 코드에 맞는 설명 |
|---|---|
| Segmentation 후 Tracking과 Depth 시작 | 원본 프레임에서 Segmentation과 Depth 동시 시작. Tracking은 Segmentation 뒤 실행 |
| 추론 결과는 Overlay·Encode를 거쳐 AVI | 코어는 `InferenceResult` 반환. 시각화·전송·저장은 외부 선택 기능 |
| Depth 모델은 ViT-S / ViT-B | 기본 설정은 UniDepth V2 ViT-B, resolution level 3 |
| GMC OFF 또는 변경 검토를 현재 구조에 포함 | sparseOptFlow GMC 유지. 프레임당 warp를 한 번 계산해 group tracker에 공유 |
| 마스크를 CPU로 가져와 거리 계산 | 기본 CUDA 경로의 마스크·Depth·median은 GPU 유지. metadata/scalar와 선택적 공개 ROI는 CPU 이동 |
| Fusion이 lifecycle까지 모두 수행 | `distance.py`는 거리 계산. `engine.py`에서 결합 후 `Lifecycle.process()` 호출 |
| Tracking이 거리값을 자동으로 안정화 | Tracking은 ID 연결. 내부 hold 정책과 공개 raw distance는 구분 |
| hold한 표시 거리가 최종 반환 | 공개 `distance_m`과 zone은 raw 기준. 내부 `display_distance_m`은 공개하지 않음 |
| 근거리 10m / 중거리 20m 경계 | 현재 기본 경계는 15m / 40m |
| 색상으로 위험 수준 확정 | 거리 구간 label만 반환. 색상은 외부 정책이며 충돌 위험 판정이 아님 |
| 특정 해상도·FPS가 엔진 고정 입력 | uint8 BGR 프레임 입력. 실제 카메라·해상도에 맞는 K 필요 |
| 모든 객체에 영구적인 고유 ID | ID switch·미연결 가능. 새 스트림마다 추적 이력 reset |
| 소실 객체의 거리도 계속 표시 | 현재 detection 없는 객체의 bbox·거리를 만들어 반환하지 않음 |
| 거리값이 정확한 카메라 직선거리 | 모델 depth의 마스크 대표값. XYZ range·최근접 표면·범퍼 거리 계산 없음 |
| 과거 ms/FPS와 30 FPS 목표를 현재 성능처럼 제시 | 과거 수치와 현재 실측을 분리. 본 문서에는 현재 FPS 보장 없음 |
| nuScenes GT·구형 provenance가 런타임 필수 | 로컬 모델 필수 파일·현재 config 사용. 과거 검증 자료에 직접 의존하지 않음 |
| 거리 계산 성공 또는 탐지 confidence가 거리 신뢰도 | 유효값만 있으면 median을 반환. 별도 거리 품질 gate·confidence는 없음 |
| low threshold 0.1이면 0.1부터 탐지 활용 | 기본 YOLO 필터 0.25 때문에 0.1~0.25 미만 detection은 tracker에 전달되지 않음 |
| gap 정책이 실제 경과 시간을 반영 | 처리 프레임 번호 기준. timestamp 기반 시간 정책은 없음 |
| bounded queue이면 전체 메모리도 항상 일정 | 프레임 대기열은 제한되지만 진단 목록·일부 ID별 이력은 누적 |
| 스트리밍 결과에 원본 이미지·영구 ID가 포함 | 결과만 반환. 외부 프레임 대응·입력 배열 보호·세션별 ID 구분 필요 |

## 15. 발표용 요약과 최종 결론

### 짧은 설명

본 프로젝트는 YOLO26m-seg의 객체 마스크와 UniDepth V2 ViT-B의 깊이맵을 결합해 사람·차량·이륜차의 대표 깊이를 추정하는 런타임이다. 원본 프레임에서 두 모델 추론을 동시에 시작하고, BoT-SORT 추적과 lifecycle 상태 처리를 입력 순서대로 수행한다. 거리 계산은 마스크 내부 positive finite depth의 정확한 median이며, 최종 반환값은 raw 거리와 ID·클래스·bbox·거리 구간·상태를 담은 메모리 객체다. 시각화·웹 전송·저장은 엔진 밖에서 선택적으로 연결한다.

### 핵심 특징

- 객체 마스크를 이용한 픽셀 선택과 GPU 거리 계산
- ReID OFF, GMC 유지 BoT-SORT 추적
- 같은 GPU의 독립 stream과 bounded ordered streaming
- Tracking·Lifecycle의 순차 상태 갱신
- 원본 거리 보존 및 내부 상태 정책과 공개 결과의 분리
- 외부 웹·DB·renderer에 연결 가능한 artifact-free API

### 한계

단안 깊이 추정·마스크 오류·조명·반사·가림·카메라 K 불일치에 따른 오차가 존재할 수 있다. 수치 반환이나 객체 confidence가 거리의 신뢰도를 보장하지 않는다. 객체 ID와 절대 거리 정확도도 보장되지 않는다. 거리 구간은 충돌 위험 판정이 아니며, 공개 raw 거리에는 내부 hold 값이 적용되지 않는다.

Lifecycle은 경과 시간이 아닌 처리 프레임 수를 기준으로 한다. 실시간 연동에서는 원본 프레임과 결과의 대응, 입력 배열 보호, 세션별 ID 구분이 필요하다. bounded queue와 장시간 전체 메모리 안정성은 별개이며, 처리 속도·거리 정확도·메모리 추이는 실제 실행 환경에서 각각 검증해야 한다.

이 프로젝트의 본질은 **“객체가 무엇이고 어떤 track에 연결되며, 그 마스크에서 추정한 대표 깊이가 얼마인지 구조화해 반환하는 병렬 추론 엔진”**이다. 결과 영상을 만드는 시스템과 연동할 수 있지만, 영상 생성 자체를 추론 엔진의 필수 동작으로 설명해서는 안 된다.
